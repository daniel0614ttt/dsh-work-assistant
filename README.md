# 工作助手（Work Assistant）

一个 DeepSeek Harness 插件：**一个可拖动的浮窗，常驻在界面上**，顶栏有两个标签页。

- **基础提示词**：选会话 → 写下原始命令 → 由 DSH 自带模型整理成结构化提示词 → 发送执行 → 完成响铃。
- **多任务管理员**：维护一份「托管清单」，把复杂目标交给模型拆成带依赖和并行分支的工作流，
  先看流程图、点确认后才真正执行。只能操作你手工加入托管清单的对话。
- **自主助理**：给它一个很大的目标（整站 / APP / 游戏 / 跨版本改造），它自己决定要开几个对话、
  怎么分工，按「骨架 → 并行模块 → 集成 → 验收」推进。不需要你预先指定任何对话。
- **设置**：自动审核的默认值、自主助理的默认项、步骤完成时是只响铃还是响铃后朗读。

审核是可选的：勾选就先看流程图再执行，不勾选就生成后直接开跑。
三个标签页都支持「自动审核权限请求」——你不在旁边时，相关且合理的授权自动同意，明显不合理的自动拒绝。

```

│ 项目                                   刷新       │

│ └───────────────────────────────────────────┘   │
```

## 它解决什么

在 DSH 里给某个项目下命令，通常要在侧边栏翻到对应会话、把口语化的需求敲进输入框。
口语命令经常缺角色、缺交付形态、缺验收标准，模型容易自由发挥。

这个插件把三件事串起来：

1. **整理**：把口语命令交给模型改写成 `#role / #goal / #context / #output /
   #constraints / #workflow / #acceptance` 七段式提示词；
2. **投递**：把整理好的提示词通过 DSH 的 `session/prompt` 接口发到你选中的会话，
   会话立刻开始执行；
3. **提醒**：盯着会话的运行状态，从「运行中」回到「空闲」时播放提示音，
   并在右上角弹一条完成横幅。

界面里没有表情符号，纯文字 + 状态色点。

## 安装

```bash
# 装进当前激活的 profile（默认 desktop）
node scripts/install.mjs

# 指定 profile
node scripts/install.mjs --profile web

# 只看会改什么，不落盘
node scripts/install.mjs --dry-run
```

安装脚本做三件事，改之前都会备份成 `*.bak-<时间戳>`：

1. 在 `~/.dsh/profiles/<profile>/node_modules/` 建一个指向本目录的软链；
2. 把 `dsh-work-assistant` 写进该 profile 的 `package.json` 依赖；
3. 在 `cordis.patch.yml` 末尾追加一条 loader 条目：

```yaml
# 工作助手：整理命令 → 发送到指定会话 → 完成后提醒
- insert:
    - id: work-assistant
      name: 'dsh-work-assistant'
```

装好后刷新一次页面（Cmd+R）。浮窗会直接出现在右下角，
侧边栏底部同时多一个「工作助手」按钮，用来显示/隐藏浮窗。

> 插件文件安装在 profile 之后，`hmr.config.root` 默认是空数组，
> **不会**监视插件自身源码的改动。改了 `lib/` 下的代码需要刷新页面
> （客户端 bundle 重新拉取）或重启应用。

### 卸载

```bash
node scripts/uninstall.mjs            # 默认 desktop
node scripts/uninstall.mjs --profile web
```

## 使用

### 两级选择：先项目，再对话

1. 浮窗默认就在右下角；拖标题栏可以挪走。
2. 顶部「项目」下拉里选项目（括号里是该项目下的对话数量，同名项目会带上级目录区分）；
3. 「对话」下拉只会列出这个项目里的对话，按最近活动排序；
4. 「原始命令」里口语化地写需求，点「整理命令」；
5. 检查「整理结果」——**可以任意修改**，不满意就再点一次整理；
6. 点「发送并执行」。浮窗可以收起或关闭，任务在后台继续；
7. 会话跑完 → 响铃 + 右上角横幅。

任务列表显示每条命令的状态：执行中 / 已完成。

**发送成功后，「原始命令」和「整理结果」两个框会自动清空**，
避免同一条命令被误发第二次；发送失败时内容保留，方便直接重试。

### 默认对话：不用每次重选

- 每个项目会记住你**上次选中的对话**；下次切回这个项目时自动用它。
- 想更稳一点，点「对话」右侧的 **设为默认**，把它固定下来（按钮变成「已固定为默认」，
  再点一次取消）。固定优先于「上次使用」。
- 项目、对话、固定关系都存在本地，刷新页面或重启应用后原样恢复。

解析顺序：**固定 → 上次使用 → 该项目最近活跃的对话**。

## 多任务管理员

### 托管清单：权限边界

切到「多任务管理员」标签，第一块是**托管清单**。

- 先选项目，再选该项目里的对话，点「加入」，这条对话才进入管理员的管辖范围。
- 只有清单里的对话会被派活，**清单外的对话一律拒绝**——即使模型在计划里编造了一个
  不存在的 sessionId，客户端也会在发指令前拦下来。
- 点条目右侧的 × 移出清单；清单变化会让已有计划失效，需要重新生成。

### 一条命令 → 一张执行图

1. 在「任务说明」里写目标，例如：
   > 把 tool 项目里的搜索功能讲清楚，再按同样的命名与接口，在另外两个项目里实现。
2. 勾选是否在计划里加入「对齐复核」步骤。
3. 点「生成执行计划」。模型只会从托管清单里挑对话，产出一张有先后依赖的图。
4. 面板会把计划画成**流程图**：同一行是没有依赖、可以并行的步骤，箭头表示先后。
5. 你确认无误后点「确认执行」，它才开始真正发指令。

实跑出来的一张图长这样（4 步，第 2、3 步并行）：

```
① 分析  梳理功能实现            （源项目）
        ↓
② 实施  在 A 项目实现  ③ 实施  在 B 项目实现
        ↓
④ 复核  审查各项目一致性
```

### 执行规则

- 依赖满足的步骤**同时发送**；有依赖的步骤要等前一步跑完并读到回复。
- 每一步的指令都不是写死的模板：执行时会把前置步骤的**真实回复**作为依据，
  交给模型生成符合 `#role / #goal / #context / #output / #constraints / #workflow / #acceptance`
  七段式的指令。这样多个项目拿到的是同一份实现说明，效果才接近。
- 每一步发出去后，插件轮询会话状态（连续两次空闲才算结束），再读回该会话最后一条
  带正文的助手回复，作为下一步的输入。
- 全部跑完会响铃，并弹出「多任务已完成」的横幅。
- 中途可以点「停止」，已发出的指令不会撤回，只是不再继续后续步骤。

### 说明

- 执行用的是 `session/prompt` 的队列模式；如果目标对话正在忙，指令会排队，等它空下来再执行。
- 计划本身不落盘：刷新页面会丢，但托管清单和任务说明会保留。
- 复核步骤只产出结论，不会自动改代码；是否按结论继续，由你决定。

## 自主助理

### 它适合什么

一次就是几十个文件、要拆成多个模块、还得有人收尾的那种活：

- 从零开发一个整站项目；
- 做一款 APP；
- 从零写一款新游戏；
- 参考你之前做过的几款 APP，再做一款同风格的新 APP；
- 把一个版本升到下一个版本，补齐整套功能。

### 怎么用

1. 顶栏切到「自主助理」。
2. 写目标：越具体越好（技术栈、运行方式、必须有的功能）。目标可以横跨多个项目。
3. 工作目录：**新建项目**会建在它下面，默认 `~/dsh-projects`。已有项目不用写在这里——
   它可以复用那些项目现有的对话和目录。
4. 决定要不要审核：
   - **勾选**：点「生成计划」→ 出流程图 → 你点「确认执行」才开跑；
   - **不勾选**：点「直接开始」→ 生成后立刻执行，不给你看中间过程。
5. 跑完响铃 + 右上角横幅。

### 多项目 + 自建对话

这是它和多任务管理员最大的区别：**不需要你预先圈定项目或对话**。

- 它会先判断目标涉及几个项目。需要新建的，在每个项目各自的目录下开工；已有的，直接复用
  那个项目现有的对话和目录。
- 每一步都带 `project` 字段（该步骤属于哪个项目），所以一张图里可以同时推进多个项目。
- `sessionMode: "new"` 的步骤，执行时才用 `session/create` 在该项目目录下**新建对话**；
  `sessionMode: "existing"` 的步骤复用已有对话，不重复开。
- 互不依赖的模块步骤会**同时**开各自的对话，各写各的模块。
- 每一步都必须声明 `module`（独占的文件/目录范围），并行模块不会去改同一批文件。
- 需要多个项目效果一致时，会先有一个骨架/分析步骤，让后续步骤都依赖它，拿到同一份契约。
- 最后有「集成」步骤拼接联调（跨项目时就是一致性核对），再由「验收」步骤给问题清单。

### 审核流程图

跨两个项目的实际例子（真跑出来的计划）：

```
① 骨架   项目A：定义共享运算契约
        ↓
② 骨架   项目B：网页骨架
        ↓
③ 模块   项目A：CLI 运算核心        ④ 模块   项目B：网页 UI 与运算
        ↓
⑤ 集成   跨项目联调与一致性核对
        ↓
⑥ 验收   两个计算器一起验收
```

同一步骤卡片上会标注它属于哪个项目（A/B 各自建在各自的目录下），流程按依赖分层，
互不依赖的同时派发。

### 权限与边界

- **权限很大**：它会在你给的工作目录里真实创建目录、写文件、跑代码。这是设计使然。
- 目录约束：新建项目目录必须落在「工作目录」下面；计划里如果写了外面的路径，会被拉回工作目录内。
  复用你已有对话时，用它所在的项目目录，不受这条限制。
- 停止只影响后续步骤：已经派出去的对话会继续跑完，不会撤回。
- 计划不落盘：刷新页面会丢计划（目标和目录会保留），需要重新生成。
- 执行前建议确认工作目录没选错——它真的会在那里写东西。

## 自动审核权限请求

三个标签页各有一个「自动审核权限请求」勾选项。勾上之后，这些对话要终端、要文件权限、
要提权时，插件会代替你判断：**和工作相关、操作合理就同意；明显不合理的直接拒绝；
拿不准的仍然留给你**。

### 它能处理什么

- 对话要跑命令、读文件、装依赖、调工具，弹出「是否允许」的卡片；
- 对话需要 `danger-full-access` 提权才能写工作区外的文件；
- 常见的终端 / 文件 / 网络工具授权。

### 怎么判断

两层：

1. **硬规则直接拒绝**：`rm -rf`、`git reset --hard`、`git push --force`、`DROP TABLE`、
   格式化磁盘、`sudo`、`curl | sh`、以及「把代码/项目/数据库全部删掉」这类说法。
2. **其余交给模型判断**：把「这个对话正在做什么 + 请求的工具 + 请求原因」交给模型，
   输出 `allow` / `deny` / `unsure`。申请提权本身不算拒绝理由，要看提权后要做的事。

模型拿不准、模型挂了、或者这条请求不属于你勾选的范围时，**不会替你拍板**，而是继续走原来的
人工审批流程。

### 为什么关掉对话也能审

判断逻辑放在 Host 侧，注册在 `approval/request` 瀑布的**最前面**。所以哪怕那个对话没有打开、
你根本没在看，请求也会被处理，不需要界面在场。

### 使用建议

- 只在你信任「这批对话 + 这个目标」的情况下打开；它会真的替你把权限给出去。
- 大改动前先扫一眼目标写得对不对——自动审核只保证「和当前工作相关」，不保证「这个工作是你想要的」。
- 想完整掌控就取消勾选，恢复成一条条手动点。

## 设置

顶栏第四个标签「设置」，包含三块：

### 自动审核权限请求

「默认打开自动审核」——初次使用或清掉本地数据后，三个标签页的自动审核开关默认是勾上的。
切换这个开关会立即应用到当前三个标签页的勾选状态。

### 自主助理默认

- 「默认勾选执行前给我审核」：切换后立即影响自主助理页的审核开关。
- 「默认工作目录」：留空等价于 `~/dsh-projects`。

### 步骤完成提示

多任务管理员和自主助理在**每一步完成时**都会：响铃 + 右上角显示「步骤完成 / 步骤标题」横幅。

- **静音**：勾上后仍然显示横幅，但不出声（提示音和朗读都停）。
- **只播放提示音**（默认）
- **提示音后朗读**：响铃约 1.2 秒后，朗读「步骤标题已完成」。

### 设置存在哪里

写在当前 profile 目录下的 `work-assistant.settings.json`：

```
~/.dsh/profiles/<profile>/work-assistant.settings.json
```

所以换浏览器、清缓存都不会丢。首次打开时如果文件不存在，会把当前浏览器的设置写上去；
新浏览器没有本地偏好，就用这份文件里的默认值。

### 待确认（当前按以下方式实现，确认后再定稿）

1. 提示音来源与音量：浏览器现场合成的三音提示，没有音量调节（只用静音开关）。
2. 横幅：右上角，9 秒自动消失，文案「步骤完成 + 步骤标题」。
3. 朗读：浏览器内置 `speechSynthesis`，语言 `zh-CN`，音色用系统默认；只念标题。
4. 自主助理「默认配置项」的范围：目前只有审核开关与默认工作目录。

## 整理出来的提示词长什么样

输入：

> 帮我建模一个 3D 机器人，并绑定骨骼。用 Blender 做，最后交付 GLB 文件。

输出（实测，deepseek-flash）：

```markdown
#role
资深 Blender 3D 建模与角色绑定工程师，具备机器人建模、骨骼绑定与 GLB 导出的专业能力。

#goal
在 Blender 中完成一个 3D 机器人的建模与骨骼绑定，并导出 GLB 文件作为最终交付物。

#context
- 项目目录：/Users/…/robot-demo
- 制作工具：Blender
- 原始需求：建模一个 3D 机器人，并为其绑定骨骼，最后交付 GLB 文件
- 待确认：项目目录中是否已有参考图、尺寸规格、风格说明或既有资产文件
- 待确认：机器人的造型风格、整体尺寸与比例、部件构成

#output
- 一个 GLB 格式文件（.glb），输出到 /Users/…/robot-demo 目录下
- 待确认：GLB 文件的具体文件名与是否需要放入子目录
- 交付物需为可直接打开查看的成品文件，而非中间稿或截图

#constraints
- 必须使用 Blender 完成建模与骨骼绑定
- 模型必须带有骨骼（Armature）绑定，不能只交付未绑定的静态模型
- 最终交付物格式必须为 GLB
- 不额外交付用户未提出的内容（如动画、渲染图、特效等），除非用户确认需要

#workflow
1. 读取项目目录，确认是否有参考素材与规格文件，列出待确认项并确认。
2. 在 Blender 中按确认的风格与比例搭建机器人模型。
3. 创建并调整骨骼（Armature），将模型各部件正确绑定。
4. 验证绑定效果：转动主要关节，确认部件随骨骼正确变形/跟随。
5. 导出 GLB 并重新导入验证骨架与模型完整可用。

#acceptance
- 项目目录下存在可打开的 GLB 文件。
- 该 GLB 能被 Blender 重新导入，且包含可见的机器人几何体。
- 导入后包含骨骼（Armature）结构，且骨骼与模型存在绑定关系。
- 活动主要关节时，对应部件随骨骼正确运动。
- 交付物仅包含用户要求的建模、绑定与 GLB 导出内容。
```

关键设计：**不确定的地方宁可写成「待确认」，也不替用户拍板**，
避免模型把猜测当成需求执行。

## 目录结构

## 实现说明

### 颜色跟随 harness

浮窗的配色全部走 harness 自己的主题变量（`--dsw-alias-bg-base`、`--dsw-alias-label-primary`、
`--dsw-alias-brand-primary` 等），所以明暗切换和自定义主题都会跟着变，不用自己维护两套色板。

当前是明是暗，优先读 `theme` 服务的 `colorScheme`；拿不到时退回 `prefers-color-scheme`
媒体查询和 DOM 变化观察。

### 浮窗为什么是 portal

浮窗挂在 `shell.overlay` 插槽里，但渲染时用 `ReactDOM.createPortal` 挂到
`document.body`：

- 应用外壳是 CSS Grid + 多个 `overflow` 容器，直接渲染会被裁切；
- 某些主题/布局会在祖先上放 `transform`，那会让 `position: fixed`
  以该祖先为定位基准，拖动坐标就全乱了。

挂到 body 之后，浮窗是真正的视口坐标，`z-index` 也压在最上层。

位置保存在 `localStorage`（键 `dsh-work-assistant:prefs:v1`），
同时记录 `open`、`minimized`、`selectedId`。

### 为什么 Host 侧零依赖

`lib/index.js` 没有 `import` 任何 `@deepseek-ai/*` 包。原因很实际：
profile 的 `~/.dsh/profiles/node_modules` 里那批软链可能指向旧版应用路径
（改过应用名之后就是断链），第三方插件一旦 `import` 内部包就会加载失败。

不依赖内部包也能暴露 RPC，靠的是 Typert Gateway 的**源码回退通道**：

- 在服务原型上挂一份
  `@deepseek-ai/dsh-typert-protocol/remote-methods` 描述符；
- 服务对象带 `typertRemote = { service, serviceKey, namespace }` 绑定；
- 用 `ctx.provide('workAssistant', service)` 注册成 cordis 服务。

Gateway 会按方法签名 `refine(request, signal)` 自动推导出 wire 参数 `request`
与取消参数 `signal`，不需要代码生成。

### 浏览器侧怎么接上

`lib/client.js` 是 `window.__ModuleLoader__.load({ id, factory })` 形式的
CJS 工厂（DSH 前端插件的固有色），只用平台模块表里的 `react`、`react-dom`
与 `zod`，再 `ctx.remote.$mount(contribution)` 挂上同名命名空间。

### 多任务管理员是怎么跑起来的

- `planFlow`：把「托管对话列表 + 任务说明」交给模型，要求只输出 JSON。
  返回后客户端做三道校验：sessionId 必须在托管清单内、依赖必须指向存在的步骤、不能有环。
  任何一条不满足就整张计划作废，不会带着可疑计划去执行。
- `composeStep`：真正发指令前，把这一步的前置步骤**真实回复**拼进去，再让模型生成
  七段式指令。所以「第 2 步」拿到的不是模板，而是第 1 步实际读到的实现说明。
- 读回复走 `session/page`：用 `session/list` 里的 `asOfSeq` 作为 `throughSeq`，
  取回最近一页事件，从后往前找 `assistant/message` 里第一段非空 `text`。
- 等待结束用的是「连续两次空闲」：会话忙完到下一轮开始之间可能有空档，
  只看到一次空闲就判定结束容易误判。
- 托管校验在 `sendManaged()` 里做最后一道拦截：即使计划被篡改，清单外的 sessionId
  也发不出去。

### 完成检测

发送成功后，插件每 3 秒读一次 `session/list`，并额外订阅
`api-session/status` 转发事件做即时触发：

- 会话 `running === true` → 记下「确实开始跑了」；
- 之后 `running === false` → 判定完成，响铃 + 横幅；
- 极短任务（发送后 6 秒内就已结束）也会被识别为完成。

### 模型失败时

`refine` 内部捕获所有模型异常。拿不到结构化结果时回退到**本地模板拼装**，
并在浮窗里显示「本地模板 · 模型不可用」，保证「整理命令」不会变成一个死按钮。

## 故障排查

| 现象 | 处理 |
|---|---|
| 右下角没有浮窗 | 刷新页面（Cmd+R）；仍没有就重启应用 |
| 浮窗被拖出屏幕了 | 拖动标题栏拉回来；或清掉 `localStorage` 里的 `dsh-work-assistant:prefs:v1` |
| 会话下拉是空的 | 点「刷新」；仍空说明 `session/list` 被拒，浮窗顶部会显示错误 |
| 点「整理命令」报错 | 浮窗会显示具体错误；模型不可用时会自动降级成本地模板 |
| 发送成功但一直「执行中」 | 会话可能卡在等待审批；处理完审批后状态会自然收敛 |
| 「生成执行计划」失败 | 模型偶尔不按 JSON 输出；点「修改条件」再点一次生成即可 |
| 计划里没有我想要的对话 | 先把它加入托管清单；模型只能从清单里挑 |
| 某一步一直等待 | 该会话可能在等审批，或模型还在跑；点「停止」可终止后续步骤 |
| 某一步报「没有读到回复」 | 该会话这一轮没有产生文本回复（例如只调用了工具），可重跑这一步 |
| 自主助理「生成计划失败」 | 模型没按 JSON 输出；点「重新规划」再试一次 |
| 自主助理没有新建对话 | 检查工作目录是否可写；新建对话失败时日志会写具体原因 |
| 自主助理跑偏了 | 点「停止」，把目标写得更具体（技术栈、运行方式、必须有的功能）后重新规划 |
| 勾了自动审核还是在等审批 | 说明模型判成了「拿不准」，交回人工了；想看原因可在宿主日志里搜 `[work-assistant] 自动审核` |
| 自动审核拒了本该通过的请求 | 说明命中了硬规则或模型判成不合理；取消勾选手动点一次即可 |
| 想彻底移除 | `node scripts/uninstall.mjs`，然后重启应用 |

备份文件在 profile 目录下：`package.json.bak-*`、`cordis.patch.yml.bak-*`。
